## 1. Decision and scope

### Development workflow gate

After a meaningful batch of changes, before a larger refactor, or when the Graphify indexed commit is noticeably behind the current Git commit, refresh the Graphify index. Use Graphify for navigation and impact analysis between refreshes; use the current Git checkout, tests and running app as the source of truth for unindexed changes.

**Continue the existing repository with a staged refactor. Do not start over.** Keep the FastAPI/Next.js foundation and reusable analytics, contracts, authentication, migrations, and tests. Extract trading orchestration from API routes and build the missing strategy runtime, simulation engine, and order management behind explicit interfaces. The current software is a research and manual paper-trading prototype; it is not yet an unattended algorithmic trading platform.

The owner confirmed **personal trading first, commercial expansion later**, and clarified that options are only one part of the intended product. The target is a complete trading platform across major instrument classes, with shared data, strategy, risk, execution, accounting, and monitoring services. NIFTY options and Upstox are the first vertical slice used to prove those services, not the platform boundary. Add equities, ETFs and futures through the same core after data, calendar, cost, margin and settlement rules for each are validated. Additional brokers and markets follow explicit adapter and operational gates. Multi-user distribution remains later scope.

The product goal is a chart-first, multi-asset market workspace inspired by TradingView, with algorithmic strategy design, testing, paper operation and eventually gated live execution integrated into the same instrument and chart context. Success means useful manual analysis as well as reproducible automated decisions, explainable risk, accurate accounting, and recoverable operations. Feature count and backtest profit are not release criteria.

### Chart-first product track

Charts, symbol discovery, watchlists, layouts, indicators, drawings, alerts, scans, replay and a trade journal are core product capabilities, not decoration around an options bot. Build them in stages: trustworthy OHLCV and candlestick/volume views; multiple documented timeframes and indicators; persisted user layouts and drawings; alert evaluation with durable delivery; then chart-linked strategy signals, replay markers and paper order inspection. Each visual state must identify its provider, exchange, interval, timestamp basis and data gaps. A chart is not evidence of an executable quote. Mobile web should offer readable chart and watchlist workflows before native packaging is considered. Follow [TradingView's feature overview](https://www.tradingview.com/features/) for capability inspiration without copying its interface or promising Pine Script compatibility.

### Confirmed trading-terminal experience

The reference supplied on 2026-09-29 confirms the primary desktop experience:

- A large central candlestick chart is the workspace, with symbol search, timeframe, chart type, indicators, layouts/save, drawing tools, undo/redo, screenshot/export and visible exchange-local clock controls.
- Buy/sell quote cards show source and freshness; they remain disabled as execution controls until the selected account, instrument, entitlement, risk and live-activation gates all pass.
- Strategy decisions appear directly on the chart as entry, stop, target, adjustment and exit markers. Selecting a marker opens the recorded decision, inputs, version, simulated/broker order lifecycle, fill assumptions and resulting P&L.
- A persistent right rail has **Signals**, **Strategies** and **Settings**. Strategy cards can be inspected, applied to the chart, removed, favorited and alert-enabled. Applying a strategy creates a draft chart instance first; paper activation is a separate explicit action and live activation remains separately gated.
- The top workspace supports multiple broker/data connections and multiple saved strategy tabs, while keeping market-data provider, execution broker and account identity visibly separate.
- Asset tabs can cover Indian equities, US equities, futures, options and permitted digital assets only when a configured provider reports the required entitlements and market rules. Unsupported markets remain visibly unavailable.
- The P&L badge must distinguish chart replay, backtest, paper and live values. Unknown or stale values stay unknown. Win rate and return claims require a reproducible dataset manifest, cost assumptions, sample count, period and out-of-sample status; unverified promotional percentages are prohibited.
- “Analyzing next entry” is backed by a persisted strategy-instance state and latest decision timestamp. It cannot be a decorative status animation.

Desktop delivery order: terminal shell and responsive panels; interactive financial chart library decision; indicators and drawings; saved layouts; strategy application and recorded markers; alerts and replay; paper controls; then broker-gated live controls. Mobile uses the same records through chart, watchlist, signal, position and emergency-control views optimized for touch.

### Replaceable data sources

Upstox is the development adapter, not a permanent data dependency. Keep market-data providers separate from execution brokers so the user can choose another data API without changing strategy definitions, chart components or account risk logic. A provider adapter must normalize instrument discovery, canonical instrument identity and provider-key mapping, OHLCV intervals, quotes, timestamp provenance, sessions, entitlements, health, rate limits and errors. Provider-specific option metadata stays behind an explicit optional capability. Store source/provider IDs with observations and watchlist mappings; never silently route an Upstox instrument key to another provider. The UI must expose the selected source and unsupported capabilities. Test a second independent adapter against shared contract fixtures before calling the system plug-and-play. Existing discovery, watchlist, capability and paper paths still contain Upstox-specific assumptions; this boundary is planned, not complete. Credentials remain server-side for every adapter, and live order adapters remain disabled until the separate M5 gate.

### First personal release

- One operator with a read-only multi-asset chart/watchlist workspace; one broker account and NIFTY options for the first automated trading vertical slice.
- Multiple independently scheduled strategy instances sharing a single account risk budget.
- Daily OHLCV charting first, then documented intraday intervals, indicators, drawings, saved layouts and alerts as data entitlements allow; visual rules and options construction, historical signal backtesting, unattended paper trading, and a monitoring console.
- One broker live pilot only after all live gates pass. Research and paper releases ship independently of live execution.
- Explicit market-session, expiry, data-quality, stale-data, failure, and end-of-day behavior.

### Deferred scope

Commercial onboarding/billing, marketplace/copy trading, multi-account allocation, arbitrary user Python execution, global asset coverage, low-latency/HFT execution, naked short options, and automatic cross-broker failover. Overnight and cross-expiry strategies require separate financing, margin, settlement, and failure controls. None should delay the first reliable vertical slice.

## 4. Architecture to evolve toward

Keep a modular monolith with separate API, strategy worker, data collector, and research-job processes. Do not introduce microservices or a large distributed streaming stack until measured load justifies them.

```text
Provider feeds / instrument master / exchange calendar
                    ↓
Validation + normalized event time + durable, versioned data
                    ↓
Strategy definition/version → strategy runtime → order intent
                                                ↓
                               Account/portfolio risk approval
                                                ↓
                               Durable OMS / execution adapter
                                  ↙                    ↘
                           Simulator                  Broker
                                  ↘                    ↙
                        Fills → ledger → reconciliation → audit
                                           ↓
                              Monitoring, alerts, dashboard
```

### Boundaries and records

- `strategy`: a validated, versioned JSON definition/AST and evaluator; no raw `eval`, broker token, or broker SDK inside strategy logic. Store instrument selection, schedule, conditions, sizing, exits, and allowed adjustments together.
- `runtime`: virtual or real clock, deterministic event ordering, indicator warm-up, state checkpoints, schedule, cooldown and restart logic. Emit an order intent with strategy-version and decision IDs.
- `risk`: deterministic checks against equity, cash, reserved margin, open positions and pending intents; atomically reserve exposure before submission. Recheck immediately before dispatch.
- `execution`: intent, order, order-event and fill models; broker-independent lifecycle with adapter capability checks. Durable idempotency keys and unique fill IDs. No claim of network-level “exactly once”; reconcile ambiguous outcomes before retrying.
- `ledger`: cash, premium, realized/unrealized P&L, fees/taxes, margin reservation/release, settlement and adjustments; balanced entries and reconciliation invariants. Do not reuse the current `EXECUTED`-only paper order table as the complete live OMS.
- `data`: raw/normalized immutable partitions, quality flags, receive/exchange timestamps, provider/source identifiers, effective-dated contract metadata and dataset manifests. PostgreSQL for transactional records; Parquet/object storage for history when justified. Redis may coordinate/cache, but must not be the only record of an accepted order intent.
- `operations`: health/readiness, metrics, correlated structured logs, alerts, restore and emergency procedures. Persist risk latches and manual interventions.

Use one strategy definition and decision evaluator across historical, paper and live modes. Adapters and clocks differ; fills will differ. Report those differences instead of claiming identical performance. Public Python SDK can wait; internal contracts and immutable versions cannot.

### Refactor sequence

1. Capture a clean source baseline and source hashes; preserve the supplied archive and original plan.
2. Add regression tests for identified defects before changing behavior.
3. Move paper orchestration, risk, ledger, quote selection and notifications out of `apps/api/main.py` into application/domain services. Keep existing routes as compatibility wrappers.
4. Split the single dashboard into research, builder, backtests, positions, execution and settings components with typed API clients.
5. Build the chart workspace and replaceable read-only provider adapter contract alongside versioned strategy records and worker execution. Prove a second adapter on fixtures before provider switching is advertised.
6. Add new OMS/ledger tables with forward migrations; preserve old paper records as legacy simulations with their original assumptions.
7. Compare old/new calculations on fixed fixtures and reconcile all migrated balances before cutover. Rollback disables new workers and preserves events; it must not erase orders or blindly downgrade financial data.

Reconsider a broader replacement only if measured refactor cost exceeds replacement cost, reuse introduces unresolvable licensing/maintenance problems, or required correctness/performance cannot be achieved. The supplied snapshot does not establish any of those conditions.

### C. Historical testing and research

### D. Unattended paper trading

Use a server worker independent of browser, JWT expiry and dashboard connectivity. Persist state and ownership; use leases/fencing or equivalent controls to stop two workers from acting on one instance. Recover after crashes without duplicate entry or exit intents.

Market-closed and stale-data behavior must be explicit. Simulated multi-leg fills must not imply atomic live execution. Include expiry settlement, zero-value options and interrupted end-of-day square-off; never invent a closing quote to make the ledger look complete.

### E. Risk and execution

Pre-trade checks: allowed market/session, contract/tick/lot/freeze rules, quote age/spread, per-order quantity/value, per-trade expiry loss, account equity, daily realized plus unrealized loss, drawdown, margin buffer, concentration, order frequency and open/pending exposure. Risk limits must account for account depletion; a percentage of starting capital alone is inadequate.

Track portfolio delta/gamma/vega and scenario shocks as data/model quality permits. Maximum expiry loss is neither required margin nor protection from legging, liquidity or operational failures.

Order lifecycle includes pending submission, acknowledged/open, partially filled, filled, cancel pending, cancelled, rejected, expired and unknown. Deduplicate callbacks; handle out-of-order events, fills after cancel requests, restart, timeout after broker acceptance, token expiry and throttling. Respect broker-supported order types and protective-order semantics; do not assume OCO/brackets or all-or-nothing baskets exist. Order timeouts are not proof of rejection. Reconcile before retrying.

Emergency controls have separate meanings: **pause entries**, **cancel outstanding orders**, **flatten positions**, and **disable the account/broker route**. Flatten is an attempted workflow whose actual fills must be verified. Cancelling all orders must not silently remove protective orders and leave exposure unprotected. Emergency state is durable and reactivation is manual after reconciliation.
